# 交通費精算Webアプリ 要件定義

- 対象: 自社精算・客先精算（SES契約における経費申請）
- 実装言語: 未定（本書はDB設計・画面設計・生成物仕様のみを対象とし、実装言語に依存しない）
- 想定利用規模: 小規模（個人〜数名、登録データ量少）

---

## 1. 背景・検討の経緯

設計にあたり、以下の代替案を検討し、理由とともに不採用とした。今後の手戻り防止のため記録しておく。

| 検討した案 | 内容 | 不採用の理由 |
|---|---|---|
| 運賃自動計算API（駅すぱあとAPI等） | 鉄道会社・路線・駅マスタを外部APIから取得し、運賃を自動計算する | フリープランは運賃を構造化データで取得できず実質有償。往復割引や運賃改定の追従など運用コストが高い。請求書には別途スクショ証跡が必須であり、証跡と自動計算結果の二重管理になる |
| Google Maps Directions/Routes API | 経路探索・運賃取得に利用できないか検討 | 公式FAQにて、日本国内の乗換案内（公共交通機関ルート）はサポート対象外と明記されている（2026年7月時点で確認済み）。利用不可 |
| Google Sheets + DuckDB | SQLiteの代わりにGoogle Sheetsを正データとし、DuckDBの`gsheets`拡張で集計する | 書き込み経路がアプリのフォーム1本のみであり、Sheetsの「人が直接編集できる」利点を活かせない。画像証跡をセルに持てずDrive連携が別途必要になる。`gsheets`はコミュニティ拡張であり継続運用の基盤としてはリスクがある。DuckDBは分析用途に限り任意で併用可 |
| スクショのOCR/LLM Vision抽出 | 登録画像から運賃・区間をAI抽出する | 事前セットアップ時に人が手入力すれば十分であり、抽出精度・確認フローの複雑化を避けられるため不要と判断 |

採用した基本方針:

- 運賃・区間・鉄道会社は、事前セットアップ時にスクショとともに**手入力**する（証跡スクショ＝正データの一次ソース）
- DBは**SQLite**（登録データ量が小規模なため）
- 証跡画像はSQLiteに**BLOBとして埋め込み保存**（バックアップ単位を1ファイルに一元化）
- 請求書PDFは生成時点の内容で**スナップショット保存**し、事後のデータ変更の影響を受けないようにする

## 3. データモデル（S1）

### 3.1 ER概要

- `fare_evidence`（区間の運賃証跡。運賃改定があれば新規行を追加し、旧行は`valid_until`で締める）
- `trips`（日々の利用実績。`fare_evidence`を選択式で参照）
- `invoices`（月末に確定した請求書PDFのスナップショット）

### 3.2 DDL

```sql
-- 区間ごとの運賃証跡
CREATE TABLE fare_evidence (
  id              INTEGER PRIMARY KEY,
  label           TEXT NOT NULL,              -- 表示名 例:"上新庄→神戸三宮"
  company_text    TEXT NOT NULL,              -- 運賃の支払先（鉄道会社）
  from_text       TEXT NOT NULL,              -- 乗車駅
  to_text         TEXT NOT NULL,              -- 降車駅
  fare_oneway     INTEGER NOT NULL,           -- 片道運賃(円)
  fare_roundtrip  INTEGER,                    -- 往復が単純2倍でない場合のみ指定。NULLならoneway*2
  image           BLOB NOT NULL,              -- 証跡スクリーンショット本体
  image_mime      TEXT NOT NULL DEFAULT 'image/png',
  valid_from      TEXT NOT NULL,              -- 'YYYY-MM-DD'
  valid_until     TEXT,                       -- NULLなら現在も有効
  created_at      TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 利用実績（カレンダー×フォームでの1件登録 = 1行）
CREATE TABLE trips (
  id                INTEGER PRIMARY KEY,
  date              TEXT NOT NULL,             -- 'YYYY-MM-DD'
  fare_evidence_id  INTEGER NOT NULL REFERENCES fare_evidence(id),
  round_trip        INTEGER NOT NULL DEFAULT 1, -- 0/1
  billing_target    TEXT NOT NULL CHECK (billing_target IN ('自社','客先')),
  created_at        TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_trips_date ON trips(date);
CREATE INDEX idx_trips_billing_date ON trips(billing_target, date);

-- 月末に確定した請求書PDFのスナップショット
CREATE TABLE invoices (
  id              INTEGER PRIMARY KEY,
  year_month      TEXT NOT NULL,               -- 'YYYY-MM'
  billing_target  TEXT NOT NULL CHECK (billing_target IN ('自社','客先')),
  pdf             BLOB NOT NULL,
  generated_at    TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE(year_month, billing_target)
);
```

### 3.3 集計クエリ例

```sql
SELECT
  t.date,
  fe.company_text,
  fe.from_text,
  fe.to_text,
  fe.fare_oneway AS 運賃,
  CASE WHEN t.round_trip
       THEN COALESCE(fe.fare_roundtrip, fe.fare_oneway * 2)
       ELSE fe.fare_oneway
  END AS "交通費(往復)"
FROM trips t
JOIN fare_evidence fe ON fe.id = t.fare_evidence_id
WHERE t.billing_target = ?
  AND t.date BETWEEN ? AND ?
ORDER BY t.date;
```

証跡添付用に、対象期間・精算先で使われた`fare_evidence_id`のユニーク集合を別途取得し、各`image`を請求書に添付する。

## 4. 画面仕様（S2）

### 4.1 区間登録（事前セットアップ）ウィザード

3ステップ形式。**DBへの書き込みはStep3の確定時に1回のみ**行い、Step1〜Step2の間はフロントエンドの状態のみで保持する（途中離脱による中途半端なレコードを防ぐため）。

```
Step1: スクショ画像を選択
  ↓
Step2: 表示名・鉄道会社・乗車駅・降車駅・片道運賃（必要なら往復運賃）を入力
  ↓
Step3: 確認画面
  - 画像プレビュー
  - Step2の入力内容一覧
  - [戻って修正する] → Step2に戻る（入力値は保持）
  - [この内容で登録する] → fare_evidenceに1行INSERT
```

### 4.2 カレンダー×フォーム画面

**左側：月間カレンダー**

- 月送り・当月に戻る操作
- 各日付にその日のtrips件数を表示
- その月の請求書確定状態（自社/客先）を視覚的に表示

**右側：選択日パネル**

- その日のtrips一覧（複数件対応、編集・削除ボタン付き）
- 「＋この日の利用を追加」フォーム
  - 区間選択（プルダウン。`valid_from <= 選択日 AND (valid_until IS NULL OR valid_until >= 選択日)`のもののみ表示。「＋新しい区間を登録する」選択肢から4.1のウィザードに遷移可能）
  - 往復チェック
  - 精算先（自社・客先）
  - 登録ボタン
- 選択日が確定済み月に属する場合、「この月の請求書は確定済みです。追加・修正しても請求書には自動反映されません」の注意書きを表示（入力自体はブロックしない）

### 4.3 請求書作成画面

```
[対象月選択]  [精算先タブ: 自社 | 客先]

確定済みの場合:
  「この月は YYYY-MM-DD HH:MM に確定済みです」
  [確定済みPDFをダウンロード]  [再生成する]

未確定の場合:
  プレビュー表（3.3のクエリ結果 + 合計行）
  証跡画像（使用区間ごとに1枚）
  [この内容でPDFを確定する]
```

- 該当tripsが0件の場合はそのタブに「対象データがありません」と表示し、`invoices`には行を作らない
- 「再生成する」押下時は「前回確定分（生成日時）を上書きします。よろしいですか？」の確認を挟んでからUPDATE
- 自社タブ・客先タブは独立して確定状態を持つ（`invoices`のUNIQUE制約による）

## 5. 請求書PDF生成仕様（S3）

- レイアウト: A4
- 生成フロー: 集計データ → Markdown組み立て → HTML変換 → PDF化（CSSで罫線・合計行の強調・`@page`によるページ設定を行う）
- 証跡画像はMarkdown内にBase64インライン埋め込み
- 列構成（自社・客先で共通、客先名等の追加列は持たない）:

| 利用日 | 鉄道会社 | 乗車駅 | 降車駅 | 運賃 | 交通費(往復) |
|---|---|---|---|---|---|
| （trips.date） | （fare_evidence.company_text） | （fare_evidence.from_text） | （fare_evidence.to_text） | （fare_evidence.fare_oneway） | （往復判定後の金額） |

- 実装上の注意: コンテナイメージにCJKフォント（Noto Sans JP等）の同梱が必須。利用日数が多い月の改ページ処理を考慮する。

## 6. 非機能要件（S4）

- コンテナでデプロイ可能な構成とする
- SQLiteのDBファイル（証跡画像・請求書PDFのBLOBを含む）1本を永続ボリュームに配置し、バックアップ対象を単純化する
- DuckDBは正データストアとしては採用しないが、`sqlite_scanner`拡張でSQLiteファイルを直接読み、月次集計・分析を行う用途では任意に利用してよい
